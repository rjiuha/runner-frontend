# CLAUDE.md

Заметки по фронтенду Runner для себя (Claude) — чтобы не перечитывать весь проект на каждый запрос.
Правь этот файл при значимых изменениях архитектуры и веди раздел «Заметки» внизу.

## Проект

React Native (Expo 56, RN 0.85, React 19) клиент игры Runner — мультиплеер, пошаговая, 2-4 игрока.
Бэкенд — отдельный репозиторий `D:\Programming\runner-game-backend` (Symfony), доступ у меня **только на
чтение**. Контракты — `D:\Programming\runner-game-backend\README.md`, правила игры — загруженный
пользователем «Правила игры.txt» (мультиплеерная настолка про гонку отрядов по трассе). Полезно свериться
с бэковым `CLAUDE.md` в его репозитории — там расписана архитектура Orchestrator/Step-сервисов и Mercure.

Запуск: `npm run start` (Expo), `npm run web`, `npm run android`. Тестов нет.

**почему**, а не что. Стилей мало (inline объекты через `StyleSheet.create`), Tailwind нет.

## Ключевые архитектурные решения

**api/client.js** — токены в памяти модуля (не в React state), один общий `refreshPromise` на все
конкурентные 401, `credentials: 'include'` для Mercure-cookie. `ApiError` — единая обёртка с
`isNetwork/isUnauthorized/isGone/userMessage`.

**useMercure** (`hooks/useMercure.js`) — протокол «слушаем SSE → буферим → грузим снапшот REST → отсекаем
буфер по version → live». **Важный фикс**: `sync()` (REST-снапшот) запускается сразу в `connect()`, а не по
событию `'open'` у EventSource. Раньше был баг: если Mercure-хаб недоступен, `'open'` не наступает никогда,
и экран висел в вечном спиннере, хотя REST прекрасно работал. Если будешь трогать этот хук — не возвращай
эту гейтировку назад.

`Lobby::toArray()` на бэке **не отдаёт поле `version`** — `normalizeLobby` подставляет 0. На финальный баг
это не влияет (редьюсеры гасят дубли по id), но при реконнекте возможна логически лишняя обработка уже
учтённых событий. Не чинил — не приоритетно, но учитывай при отладке рассинхрона лобби. У `RunnerGame`
такого бага **больше нет** — пользователь сам добавил `version` в `RunnerGame::toArray()` на бэке
(`Entity/RunnerGame.php:420`), перепроверено чтением файла.

**Screen.js** — общий каркас всех обычных экранов: SafeAreaView + `ParallaxBackground` (единый на все
экраны, рендерится тут один раз, а не в каждом экране) + опциональный scroll/KeyboardAvoidingView. Экран
логина/меню/лобби всегда через `<Screen>`. **GameBoardScreen — исключение**, он полноэкранный и рулит
раскладкой сам (без safe-area отступов), но тоже вставляет `<ParallaxBackground />` вручную для
единообразия фона.

**Ориентация GameBoardScreen** — с 2026-08-31 (шестой заход) `orientation` из `useBoardLayout`
(`'landscape'/'portrait'` по фактическому соотношению `screenW`/`screenH`, адаптивно и на вебе через
ресайз окна, и на мобильных через физический поворот) управляет ТОЛЬКО расположением ПАНЕЛИ игрока —
слева на широком окне ('landscape'), снизу на узком ('portrait'). Сама ДОРОГА (`BoardGrid`) — ВСЕГДА
рисуется в портретной геометрии (вертикальные дорожки, скролл по вертикали, стрелки вверх/вниз),
независимо от `orientation` — `<BoardGrid orientation="portrait">` в `GameBoardScreen` захардкожен, не
завязан на хук. До этого захода `orientation` управлял ОБЕИМ осями сразу (была отдельная "альбомная"
геометрия дороги — горизонтальные дорожки) — разделено по прямому запросу пользователя. `useBoardLayout`
считает геометрию дороги ОДНОЙ общей функцией (`computeRoadGeometry`) от прямоугольника, который ей
достаётся (после вычета места под панель — слева или снизу, в зависимости от `orientation`), а не двумя
раздельными ветками. Кнопки навигации вверх/вниз (не mobileNav-случай, см. ниже) — КОЛОНКОЙ СЛЕВА от
дороги (седьмой заход того же дня, было сверху/снизу), ассет `RoadNavButton` (тот же, что у mobileNav),
размер `navBtnSize` — ВСЕГДА половина размера сегмента, возвращается прямо из `computeRoadGeometry`
(параметр `reserveNavColumn` — учитывает ширину колонки кнопок ПРИ расчёте самого сегмента, замкнутая
форма: делит бюджет ширины на `ROWS+0.5`, а не на `ROWS`, см. комментарий в файле). **Движение по трассе
идёт снизу вверх** (начало трассы — у панели игрока) —
реализовано в `BoardGrid` через `flexDirection: 'column-reverse'` (чисто layout-свойство, без
transform/отражений — старая версия на `transform: scaleY(-1)` заменена ещё в пятнадцатом-шестнадцатом
заходах 2026-08-13, эта строка была не обновлена вовремя), подробности и вся геометрия разобраны в шапке
`BoardGrid.js`. `useAdaptiveOrientation` (бывший `useLockLandscape`) на мобильных снимает системный лок
ориентации на время экрана сессии и возвращает portrait-лок при уходе — раскладку выбирает сам экран
через `orientation`, не через системный поворот. Координаты ячеек (`cell.id`/`row`/`col`/`blockIndex`,
которые видит `GameBoardScreen.handleCellPress`) от `orientation` не зависят вообще — вся игровая логика
(SELECT/MOVE/SHOOT/подсветка) не в курсе, где сейчас панель.

**GameBoardScreen** — с Фазы 1 (см. запись 2026-08-12, седьмой заход, ниже) подключён к реальному
`GET /api/runner_game` + Mercure-топику `runner_game_{id}` через `useMercure`/`runnerGameReducer`, тем же
протоколом «буфер → снапшот → live», что и `LobbyScreen`. Раскладка: слева `PlayerInfoPanel`
(переключатель игроков, кубики, drag-and-drop на зоны усилений через
`react-native-gesture-handler`+`reanimated`, карточки бегунов), справа `BoardGrid` (сетка 6×8×3 сегмента,
скролл через `useBoardScroll`: PanResponder на мобильных, `useScrollAnimation` на вебе). Геометрия —
`useBoardLayout`, считает так, чтобы один фрагмент 8 колонок помещался в правую зону без обрезки.
`lib/board.js` разворачивает `trackBegin/Middle/End` в плоский список ячеек и резолвит типы клеток
(`danger_2/danger_3` → `danger`, `anomaly` → `danger`, нет данных → `road`). С Фазы 2 (запись
2026-08-12, девятый заход, ниже) select/move/collision/shoot/ability вызывают реальный бэк.
**Принципиально: локального стейта "что назначено" в GameBoardScreen нет** — как только SELECT/ABILITY
проходят, `runner.dice`/`player.ability`/`player.diceN` обновляются live-событиями
(`runnerGameReducer`), и UI просто читает их напрямую (см. `PlayerInfoPanel`/`RunnerCard`). Единственный
переходный локальный стейт — `pendingAbility` (heal/reaper ждут второй тап после дропа кубика на зону,
т.к. бэк принимает `runnerId`/`positionX/Y/segment` одним вызовом `/ability`, а не двумя шагами).
Подсветка легальных клеток (MOVE/SHOOT/reaper-размещение/первый выход на трассу) — `lib/hexDirection.js`
(`forwardNeighbors`), зеркалит `DirectionService::run()`+`canShoot()` на бэке.

**Партия имеет собственный ready-up гейт, отдельный от лобби**: после `game_created` (лобби) игра
рождается со статусом `waiting`, и каждый игрок обязан вызвать `POST /runner_game/start`, прежде чем
статус станет `active` (событие `game_active`). `GameBoardScreen` рисует `GameWaitingRoom` при
`status === GAME_STATUS.WAITING` и сам переключается на доску, когда статус меняется — доп. навигации не
нужно, компонент просто по-другому рендерит тот же live-стейт.

**Коллизия сигналится НЕ через `player.step`** (в бэковом enum `PlayerStep` нет кейса COLLISION) — а через
`game.extraTurnPlayer`/поле `extraTurnPlayer` события `game_turn_changed`. Пока оно не `null` — бэк
блокирует вообще все игровые действия всем игрокам, и никакого таймаута на бэке нет: если игрок-цель не
ответит на `/collision`, партия зависает навсегда. Фронт (Фаза 1) это не резолвит, только показывает
баннер и через 18 сек даёт кнопку ручного `resync()` — см. `GameBoardScreen.COLLISION_STUCK_TIMEOUT`.

`GestureHandlerRootView` обязателен в `App.js` (уже добавлен) — без него драг кубиков молча не работает на
Android.

**Анимации бегунов (Скаут/Солдат/Атлет — `RUNNER_TYPES.SPRINTER/ATHLETE/TANK`)** — начало Фазы 3, см.
`2026-08-31` в «Заметки» ниже за полную историю живого тестирования и найденные баги. Архитектура:
- `constants/runnerAnimations.js` — реестр gif-ассетов на `{type, status}`, только для типов, для которых
  реально есть набор: скаут (`assets/images/runners/scout/`), солдат (`.../trooper/`,
  `RUNNER_TYPES.ATHLETE` — не путать с папкой, названия разъехались после переименования лейблов, см.
  находку 2026-08-31 в «Заметки»), атлет (`.../athlet/`, `RUNNER_TYPES.TANK`) — `getRunnerAnimationImage`/
  `getRunnerAvatarImage` возвращают `null` для остальных типов (пока только Жнец), и `RunnerToken` сам
  откатывается на старую статичную иконку (`RUNNER_DISPLAY[type].icon`) — добавление анимаций следующему
  типу бегуна требует только новую запись в этом реестре, без правок компонентов.
- **Перекраска неона под цвет игрока** (2026-08-31, см. находку в «Заметки»): каждая запись в реестре —
  не один gif, а пара `{base, mask}`. `base` — тот же кадр, но неоновые вставки обесцвечены (десатурация
  с сохранением светлоты) в тон тёмного костюма. `mask` — те же кадры, только неон залит чистым белым на
  прозрачном фоне, всё остальное прозрачно. `RunnerToken` рисует пару ДВУМЯ наложенными `<Image>`: base
  как есть, mask поверх с `tintColor={color}` (цвет игрока, уже приходил в компонент) — так неон красится
  в цвет команды, а сам спрайт (тёмный костюм, метки повреждений и т.п.) не трогается. Обе гифки на пару
  сгенерированы автоматически скриптом (порог по HSL: `hue 150–255°, saturation ≥20%, lightness 35–96%`)
  из оригинальных ассетов пользователя — сам скрипт не сохранён в репозитории (одноразовый, в scratchpad
  сессии), но порог задокументирован здесь на случай, если понадобится перегенерировать. Оригинальные
  (без суффикса) gif оставлены в assets — код их больше не использует, но на случай пересчёта порога они
  нужны как исходники.
- `hooks/useRunnerAnimations.js` — стейт-стор `{ [runnerId]: {kind, direction?/side?, nonce, fromStatus?} }`
  с автооткатом в `idle` по таймауту (`kind`: move/attack/gotShot/fly/destroyed; `destroyed` — терминально,
  без отката). **Очередь по runnerId** (2026-08-31, второй заход): `trigger()` не перезаписывает текущую
  анимацию мгновенно, а кладёт шаг в очередь конкретного бегуна — играются по одному, каждый свою полную
  длительность, прежде чем начать следующий. Нужно для каскадов (отскок от столкновения → аномалия →
  отлёт из неё, несколько `runner_save` почти одновременно) — раньше все промежуточные шаги схлопывались
  в последний trigger (жалоба пользователя: бегун "телепортировался" в клетку аномалии, показывалась
  только финальная анимация). Единственное исключение — `pending`-слияние: `step_move` (транзиентный,
  даёт направление раньше позиции) метит свой шаг `pending: true`, и следующий `runner_save` с той же
  передвижкой ДОПОЛНЯЕТ его позицией на месте, а не заводит второй слот — иначе обычный некаскадный шаг
  играл бы вдвое дольше. **`anomaly`-заготовка (2026-09-01)** — тот же pending-приём, но с `kind:'fly'`
  вместо `'move'`, и мердж СПЕЦИАЛЬНО НЕ даёт входящему `trigger()`-вызову (реальный `runner_save` отлёта)
  подменить `kind` — если заготовка уже была `'fly'`, результат мерджа тоже `'fly'`, даже если следующий
  `runner_save` по эвристике forwardNeighbors формально выглядел бы как обычный шаг вперёд (`'move'`).
  Раньше выход из аномалии мог случайно отрисоваться как ходьба вместо перелёта — по прямому запросу
  пользователя зафиксировано жёстко. Второй экспорт хука — `visualPositions[runnerId]`: пока у бегуна есть
  незавершённая очередь, `BoardGrid` рисует его в позиции ТЕКУЩЕГО шага очереди (проп
  `runnerVisualPositions`), а не в реальной (уже полностью применённой в game-стейте) — иначе
  промежуточные "остановки" каскада не отрисовались бы ни одним кадром, `RunnerTokenSlide` заскользил бы
  сразу к финальной точке. `reset()` — сбрасывает очереди/таймеры/визуальные позиции, вызывается вместе
  с ручным `resync()` (кнопка при зависшей коллизии) — REST-рефетch подменяет game-стейт целиком, минуя
  событийный поток, который двигает очередь, без сброса застрявшая очередь держала бы бегуна в позиции
  старого шага. `lib/runnerAnimTriggers.js` — чистые функции "Mercure-событие → что триггернуть":
  `handleVersionedRunnerAnimEvent` смотрит на versioned-события ДО применения `runnerGameReducer` (нужно
  старое состояние для сравнения), кладёт `toPosition` в каждый `trigger` про перемещение;
  `handleTransientRunnerAnimEvent` — на транзиентные (`step_move`/`step_shoot`/`anomaly`). **Важно про
  knockback/`fly`**: бэк НЕ шлёт отдельного сигнала "этого бегуна оттолкнуло туда-то" (событие `collision`
  несёт `direction`, но не id бегуна — см. находку в «Заметки», 2026-08-31) — используется эвристика: если
  новая позиция из `runner_save` НЕ является forward-соседом старой (`lib/hexDirection#forwardNeighbors`),
  это трактуется как отскок/телепорт → `fly`. Осознанно принятый компромисс, не 100%-надёжный сигнал.

  при ЛЮБОЙ будущей правке позиционирования токенов** — разный box size между рендерами того же

### Известные грабли RN/Android (проверено на практике, не теория — держать в уме для ЛЮБОГО нового
компонента с картинками/анимациями/9-slice-декором, не только для тех, где это уже словили)

- **`resizeMode="repeat"` на Android НЕ учитывает плотность экрана** — тайл рисуется в физических
  пикселях файла 1:1, независимо от `dp`/`PixelRatio`, из-за чего на плотных экранах получается заметно
  мельче задуманного, рассинхронизируясь с соседними `stretch`-элементами. Тайлить только явными
  `resizeMode="stretch"`-копиями нужного размера (см. `components/ui/TiledImage.js`), не через `repeat`.
- **`onLayout` на абсолютно спозиционированном (`position:'absolute'`) элементе внутри родителя с
  AUTO-высотой на Android может стабильно вернуть 0** — родитель ещё не устаканил размер к этому
  измерению. Мерить такой размер через `measureInWindow` на реальном flow-элементе снаружи, не
  полагаться на `onLayout` самого абсолютного потомка.
- **Дробные (нецелые) пиксельные размеры/позиции соседних тайлов 9-slice-мозаики** (`TiledImage`/
  `PersonPanel`/`FramePanel`) **дают швы на Android** — Skia округляет каждый тайл независимо, соседи не
  гарантированно совпадают по границе. Всегда `Math.round()` ИТОГОВЫЕ размеры/позиции тайлов, не сам
  коэффициент масштаба.
- **Большой многострочный PNG-спрайт-лист (сотни KB decoded, единицы МБ) рендерится РАЗМЫТО на Android
  независимо от способа вырезания окна/масштабирования** (transform vs left/top, scale=1 vs честный
  масштаб) — точный механизм не установлен (не лимит текстуры GPU), но воспроизводимо и лечится
  нарезкой на отдельные файлы поменьше, по одному на анимацию/строку (см. `constants/
  spritePackStrips.js`).
- **`transform: X ? [...] : undefined` в стиле — краш** (`_validateTransforms`, `Cannot read property
  'forEach' of null`) — ключ `transform` не должен присутствовать со значением `undefined`, только
  реальным массивом либо отсутствовать целиком. Компоновать через `[base, condition && extra]` в
  массиве стилей, не тернарник на весь `transform`.
- **JS `setTimeout` НЕ синхронизирован с внутренними "часами" зацикленной (`loop:0`) анимации/gif** —
  внешний таймер может опоздать на десятки миллисекунд относительно реального конца цикла, и
  зацикленный ассет успевает показать кадр 0 повторно ДО того, как внешний код успеет скрыть/сменить
  его. Давать запас минимум в 2 кадра (не 1) до конца анимации у любого внешнего таймера, привязанного
  к её длительности.
- **`Animated.Text`/`Animated.Image` НЕ обходят внешний JSX-патч**, если тот матчит компонент по
  `type === Text`/`Image` — `createAnimatedComponent` рендерит НАСТОЯЩИЙ `<Text>`/`<Image>` внутри,
  транспилируемый тем же jsx-рантаймом, патч всё равно срабатывает.
- **CSS `animationKeyframes` (react-native-web) применяется ТОЛЬКО через `StyleSheet.create()`**, не как
  голый инлайн-объект стиля — иначе duration/direction применятся как обычные CSS-свойства, а
  `animation-name` останется `none`, и анимация физически не запустится.

**Известные бэковые баги (read-only — не трогать, только сообщать бэкенд-разработчику):**

- `ReaperService::validateCell()` сравнивает `Cell::getType()` (`string`) с `RoadType::WALL`/`ANOMALY`
  через `===` — всегда `false` в PHP (enum-кейс не равен строке), сервер реально не запрещает ставить
  Жнеца на непроходимую клетку. Фронт сам проверяет проходимость/занятость при подсветке легальных мест.
- `POST /runner_game/ability` с `{"accept":false}` БЕЗ ключа `details` падает `500` (нетипизированное
  `AbilityDto::$details`, nullsafe не спасает при отсутствующем ключе). Фронт учитывает —
  `api/runnerGame.js#ability(accept, details = null)`, никогда `undefined`.
- `Collision::ballCollision()` в ветке "Мяч инициатор, реальный игрок крупнее" передаёт `lowRunner`/
  `topRunner` в порядке, который выглядит перевёрнутым относительно семантики "TOP — крупная сторона" —
  влияет только на редкий edge-case (`saveCollision`'s ранний return при уже DESTROYED/BROKEN раннере).
- `RunnerPlayerViewModel::$step` типизирован `?string` вместо `?int` (коммит `59aea0f`, 2026-09-24) —
  REST-снапшот отдаёт `step` строкой вместо числа, ломая строгие сравнения. Фронт защитно приводит через
  `Number(...)` в `api/normalize.js#normalizeRunnerGame` — работает независимо от того, поправят ли бэк.
- `DirectionService::run()` даёt LEFT_UP/RIGHT_UP чисто боковым шагом на чётном `positionX` и диагональю
  на нечётном — фронт (`lib/hexDirection.js#neighborPosition`) больше НЕ зеркалит эту чётность (по
  прямому запросу пользователя — стрелять/подсвечивать только строго вперёд, независимо от чётности).
  Остаточный риск: если бэк применит чётный ход как боковой (не диагональ), после тапа бегун может на
  миг визуально разойтись с подсвеченной клеткой — расхождение само исчезает на следующем live-событии.
