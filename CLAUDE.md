# CLAUDE.md

Заметки по фронтенду Runner для себя (Claude) — чтобы не перечитывать весь проект на каждый запрос.
Правь этот файл при значимых изменениях архитектуры и веди раздел «Заметки» внизу.

## Проект

React Native (Expo 56, RN 0.85, React 19) клиент игры Runner — мультиплеер, пошаговая, 2-4 игрока.
Бэкенд — отдельный репозиторий `D:\Programming\runner-game-backend` (Symfony), доступ у меня **только на
чтение**. Контракты — `D:\Programming\runner-game-backend\README.md`, правила игры — загруженный
пользователем «Правила игры.txt» (мультиплеерная настолка про гонку отрядов по трассе). Полезно свериться
с бэковым `CLAUDE.md` в его репозитории — там расписана архитектура Orchestrator/Step-сервисов и Mercure.

Запуск: `npm run start` (Expo), `npm run web`, `npm run android`. Тестов нет.

## Структура

```
src/
  api/         клиент + эндпоинт-модули (client.js — токены/refresh/retry, ApiError, normalize.js,
               lobby.js, runnerGame.js)
  components/
    ui/        общие виджеты (Screen, Button, Input, ParallaxBackground)
    menu/      главное меню
    game/      всё про игровую доску (см. ниже), включая GameWaitingRoom (пред-игровой ready-up)
  config/      env.js — API_URL/MERCURE_URL, зависят от Platform.OS (эмулятор Android = 10.0.2.2)
  constants/   GameConstants.js (зеркалит бэковые enum'ы), mockGameData.js (заглушка ответа бэка,
               использовалась до подключения GameBoardScreen к реальному API)
  context/     AuthContext (обёртка над api/auth + токены)
  hooks/       useAuth (реэкспорт AuthContext), useMercure, useBoardLayout/useBoardScroll/useScrollAnimation/useLockLandscape
  lib/         мелкие утилиты без React (board.js, jwt.js, notify.js, storage.js, eventSource.js,
               hexDirection.js — гекс-соседи клетки, зеркало DirectionService на бэке)
  navigation/  RootNavigator (auth-gate), routes.js
  screens/     AuthScreen, MainMenuScreen, LobbySearchScreen, LobbyScreen, GameBoardScreen
  store/       lobbyReducer.js, runnerGameReducer.js — чистые редьюсеры для Mercure-событий
  theme/       единственный источник colors/spacing/font/radius/shadow
```

Конвенция файла: первая строка — комментарий с путём (`// src/screens/Foo.js`). Комментарии объясняют
**почему**, а не что. Стилей мало (inline объекты через `StyleSheet.create`), Tailwind нет.

## Ключевые архитектурные решения

**api/client.js** — токены в памяти модуля (не в React state), один общий `refreshPromise` на все
конкурентные 401, `credentials: 'include'` для Mercure-cookie. `ApiError` — единая обёртка с
`isNetwork/isUnauthorized/isGone/userMessage`.

**useMercure** (`hooks/useMercure.js`) — протокол «слушаем SSE → буферим → грузим снапшот REST → отсекаем
буфер по version → live». **Важный фикс**: `sync()` (REST-снапшот) запускается сразу в `connect()`, а не по
событию `'open'` у EventSource. Раньше был баг: если Mercure-хаб недоступен, `'open'` не наступает никогда,
и экран висел в вечном спиннере, хотя REST прекрасно работал. Если будешь трогать этот хук — не возвращай
эту гейтировку назад.

`Lobby::toArray()` на бэке **не отдаёт поле `version`** — `normalizeLobby` подставляет 0. На финальный баг
это не влияет (редьюсеры гасят дубли по id), но при реконнекте возможна логически лишняя обработка уже
учтённых событий. Не чинил — не приоритетно, но учитывай при отладке рассинхрона лобби. У `RunnerGame`
такого бага **больше нет** — пользователь сам добавил `version` в `RunnerGame::toArray()` на бэке
(`Entity/RunnerGame.php:420`), перепроверено чтением файла.

**Screen.js** — общий каркас всех обычных экранов: SafeAreaView + `ParallaxBackground` (единый на все
экраны, рендерится тут один раз, а не в каждом экране) + опциональный scroll/KeyboardAvoidingView. Экран
логина/меню/лобби всегда через `<Screen>`. **GameBoardScreen — исключение**, он полноэкранный и рулит
раскладкой сам (без safe-area отступов), но тоже вставляет `<ParallaxBackground />` вручную для
единообразия фона.

**Ориентация GameBoardScreen — адаптивная** (с 2026-08-13, см. запись "четырнадцатый заход" ниже), не
жёстко альбомная: `useBoardLayout` сам выбирает `orientation` ('landscape'/'portrait') по фактическому
соотношению `screenW`/`screenH` из `useWindowDimensions` при каждом рендере (работает и на вебе через
ресайз окна, и на мобильных через физический поворот устройства). `useAdaptiveOrientation` (бывший
`useLockLandscape`) на мобильных просто снимает лок ориентации на время экрана сессии и возвращает
portrait-лок (как у всего остального приложения, см. `app.json`) при уходе с экрана — саму раскладку
экран выбирает сам через `orientation`, не через системный поворот. В портретной раскладке доска
рисуется сверху (скролл по вертикали, стрелки вверх/вниз) и **движение по трассе идёт снизу вверх**
(начало трассы — у панели игрока, внизу экрана) — реализовано в `BoardGrid` через отражение
(`transform: scaleY(-1)`) с контр-отражением листовых визуальных элементов, подробности и вся геометрия
разобраны в шапке `BoardGrid.js`. Панель игрока в портретной раскладке — под доской, той же ширины, что
экран, с фиксированной высотой (`panelH` из `useBoardLayout`, в отличие от альбомной, где панель слева
фиксированной ШИРИНЫ и тянется на всю высоту). Координаты ячеек (`cell.id`/`row`/`col`/`blockIndex`,
которые видит `GameBoardScreen.handleCellPress`) от ориентации не зависят — меняется только то, как
`BoardGrid` их визуально раскладывает, так что вся игровая логика (SELECT/MOVE/SHOOT/подсветка) работает
в обеих раскладках без изменений.

**GameBoardScreen** — с Фазы 1 (см. запись 2026-08-12, седьмой заход, ниже) подключён к реальному
`GET /api/runner_game` + Mercure-топику `runner_game_{id}` через `useMercure`/`runnerGameReducer`, тем же
протоколом «буфер → снапшот → live», что и `LobbyScreen`. Раскладка: слева `PlayerInfoPanel`
(переключатель игроков, кубики, drag-and-drop на зоны усилений через
`react-native-gesture-handler`+`reanimated`, карточки бегунов), справа `BoardGrid` (сетка 6×8×3 сегмента,
скролл через `useBoardScroll`: PanResponder на мобильных, `useScrollAnimation` на вебе). Геометрия —
`useBoardLayout`, считает так, чтобы один фрагмент 8 колонок помещался в правую зону без обрезки.
`lib/board.js` разворачивает `trackBegin/Middle/End` в плоский список ячеек и резолвит типы клеток
(`danger_2/danger_3` → `danger`, `anomaly` → `danger`, нет данных → `road`). С Фазы 2 (запись
2026-08-12, девятый заход, ниже) select/move/collision/shoot/ability вызывают реальный бэк.
**Принципиально: локального стейта "что назначено" в GameBoardScreen нет** — как только SELECT/ABILITY
проходят, `runner.dice`/`player.ability`/`player.diceN` обновляются live-событиями
(`runnerGameReducer`), и UI просто читает их напрямую (см. `PlayerInfoPanel`/`RunnerCard`). Единственный
переходный локальный стейт — `pendingAbility` (heal/reaper ждут второй тап после дропа кубика на зону,
т.к. бэк принимает `runnerId`/`positionX/Y/segment` одним вызовом `/ability`, а не двумя шагами).
Подсветка легальных клеток (MOVE/SHOOT/reaper-размещение/первый выход на трассу) — `lib/hexDirection.js`
(`forwardNeighbors`), зеркалит `DirectionService::run()`+`canShoot()` на бэке.

**Партия имеет собственный ready-up гейт, отдельный от лобби**: после `game_created` (лобби) игра
рождается со статусом `waiting`, и каждый игрок обязан вызвать `POST /runner_game/start`, прежде чем
статус станет `active` (событие `game_active`). `GameBoardScreen` рисует `GameWaitingRoom` при
`status === GAME_STATUS.WAITING` и сам переключается на доску, когда статус меняется — доп. навигации не
нужно, компонент просто по-другому рендерит тот же live-стейт.

**Коллизия сигналится НЕ через `player.step`** (в бэковом enum `PlayerStep` нет кейса COLLISION) — а через
`game.extraTurnPlayer`/поле `extraTurnPlayer` события `game_turn_changed`. Пока оно не `null` — бэк
блокирует вообще все игровые действия всем игрокам, и никакого таймаута на бэке нет: если игрок-цель не
ответит на `/collision`, партия зависает навсегда. Фронт (Фаза 1) это не резолвит, только показывает
баннер и через 18 сек даёт кнопку ручного `resync()` — см. `GameBoardScreen.COLLISION_STUCK_TIMEOUT`.

`GestureHandlerRootView` обязателен в `App.js` (уже добавлен) — без него драг кубиков молча не работает на
Android.

## Известные пробелы / TODO (актуально на момент записи)

- **Накат (select type=ROLL) не реализован.** Дополнительный ход уже двигавшимся бегуном (до 2 раз за
  раунд), доступен только если у игрока не осталось неперемещённых исправных бегунов. Сознательно
  отложено в Фазе 2 (отдельная, самостоятельная проверка готовности по всем раннерам игрока).
- **Атака Жнеца сразу при размещении не реализована.** `ability=reaper` поддерживает опциональный
  `direction` в том же вызове — фронт сейчас всегда шлёт `direction: undefined` (только размещение).
- **Переход бегуна за передний край видимого сегмента не реализован.** Если `positionX` бегуна
  переполняется за пределы 3 загруженных сегментов (см. `lib/hexDirection.js`), клетка для тапа
  физически не отрисована — `forwardNeighbors` такую клетку просто не включает в подсветку. Нужна
  отдельная UI-аффорданса (кнопка/стрелка «съехать с трассы»), не наступали на это ещё живьём.
- **Анимации/очередь transient-событий — Фаза 3.** `onTransient` в `useMercure`-вызове `GameBoardScreen`
  сейчас no-op; `step_*`/`danger`/`collision`/`damage`/`ricochet`/`rocket`/`stupor`/`anomaly` не
  используются для покадровых реплик. **Важно**: один вызов `/move` может сдвинуть бегуна больше чем на
  1 клетку за раз, если клетка с закрытым жетоном опасности вскрывается в Anomaly/Stupor — бэк сам
  цепляет ещё один(и) `Action::TYPE_MOVE` внутри той же транзакции (см. живой прогон в «Заметки» ниже,
  девятый заход). Фронт это не ломает (стейт всё равно строится из live-данных, а не из локального
  предположения "куда должен был прийти тап"), но будущей анимации нужно уметь проигрывать НЕСКОЛЬКО
  `runner_save` подряд на один пользовательский тап, а не 1-в-1.
- **`Runner.damageTokens` — выдуманное поле.** У бэка `Runner::toArray()` отдаёт только `status`
  (healthy/damaged/broken/destroyed), **без** типа конкретного жетона повреждения. UI по ТЗ должен
  показывать тип — либо просить бэк добавить поле, либо копить типы на фронте из потока событий
  (`danger`/`damage`/`ricochet`/`rocket`/`stupor`/`anomaly`).
- **`RunnerPlayer::toArray()` не отдаёт `activeRunner`.** Это поле есть только в событиях (`player_step`,
  `step_selection`, `ability_*`) — `runnerGameReducer` его туда кладёт по мере поступления событий, но
  сразу после reconnect (до первого такого события) поле будет `undefined`. Осознанный пробел, не баг.
- На бэке подтверждённый (не мой) баг: `ReaperService::validateCell()` сравнивает `Cell::getType()`
  (`string`) с `RoadType::WALL`/`RoadType::ANOMALY` через `===` — это всегда `false` в PHP (enum-кейс не
  равен строке), т.е. сервер реально не запрещает ставить Жнеца на стену/аномалию. Фронт (Фаза 2) сам
  проверяет проходимость и занятость клетки при подсветке легальных мест для Жнеца
  (`GameBoardScreen` — `rawCellType`/`findRunnerAt` в вычислении `highlightedCells`), не полагаясь на бэк.
- **Найденный живьём баг бэка**: `POST /runner_game/ability` с `{"accept":false}` без ключа `details`
  падает `500 Internal Server Error` (нетипизированное свойство `AbilityDto::$details` остаётся
  неинициализированным, если ключ отсутствует в JSON — nullsafe `?->` не спасает от этой ошибки, это не
  то же самое, что `null`). Явный `{"accept":false,"details":null}` работает нормально (проверено
  curl'ом). `api/runnerGame.js` учитывает это — `ability(accept, details = null)`, НЕ `undefined`
  (`JSON.stringify` выкидывает `undefined`-поля из тела, так что дефолт обязателен именно `null`).
- `config/env.js`: `LAN_IP` — плейсхолдер, для теста на физическом устройстве надо подставлять реальный IP
  вручную (закомментированная строка в `devHost()`).
- Ассеты: изображения теперь разложены по подпапкам `assets/images/{road,dice,runner}` — если добавляешь
  новый набор ассетов, тоже заводи подпапку, а не кидай в корень `images/`.
